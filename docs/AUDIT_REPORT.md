# TagMarket Audit

Дата аудита: 2026-10-01. Проверена чистая `main`, commit `fb3302d7ffd3cbe8f354b91c097248f2923f4a67`.

## 1. Current state

TagMarket состоит из Windows-агента MT5, aiohttp-сервера/Telegram-бота и Mini App без frontend-сборки. Счета хранятся в accounts.json с шифрованием паролей; сделки, состояние MT5 и сводки — в SQLite; сервер и агент синхронизируются HTTP API с общей арендой опроса. Документация описывает запуск, выкладку и ручные проверки; автотесты используют временные данные.

В корне отсутствует `AGENTS.md`; `docs/ROADMAP.md` и `docs/ARCHITECTURE.md` также отсутствуют. Для проекта задан другой корневой набор инструкций с «lazy senior dev» правилами. README и MINIAPP в основном соответствуют коду. Отмеченные в `docs/findings.md` уже исправленные пункты здесь не повторяются. Некоторые его незакрытые пункты (`share` input validation, одинаковые движения портала в одну секунду и неполное покрытие страниц) всё ещё подтверждаются, но классифицированы ниже.

## 3. Critical findings

### AUD-01 — P1 · Команда перезапуска подтверждается до выполнения

- Компонент: торговый агент / команды
- Файл: `agent.py:866-877`, `webhook_server.py:422`, `store.py:248-256`
- Проблема: агент оборачивает `taskkill` в `except Exception`, но выставляет `done = True` даже при ошибке. `subprocess.run` также не проверяет ненулевой exit code по умолчанию. Затем сервер сохраняет пакет состояния и удаляет команду по `command_done`.
- Условия: `taskkill` недоступен/завершился исключением либо процесс терминала нельзя завершить.
- Последствия: фактический перезапуск не произведён, но очередь очищена; команда не повторяется и UI сообщает об успешной отправке.
- Статус: `FIXED` в текущей рабочей копии. `_restart_terminal()` проверяет код/исключение `taskkill`, затем проверяет отсутствие процесса; `collect()` выставляет `command_done` только после успешной проверки. Ошибка оставляет ack выключенным. Regression test покрывает формирование sync payload при сбое.
- Остаточный runtime check: на Windows проверить с тестовым терминалом сценарии «процесс уже закрыт», «taskkill не завершил процесс» и «доступ запрещён»; реальные торговые действия не запускать.

### AUD-02 — P1 · Нет долговечной очереди для webhook уведомлений

- Компонент: webhook / доставка уведомлений
- Файл: `webhook_server.py:101-153`, `webhook_server.py:209-242`
- Проблема: webhook помечает событие просмотренным до фоновой доставки (`fire`). `notify()` делает до трёх попыток и после неудачи возвращает `None`; входящий повтор затем отсекается `partner.unseen()`. Неудача доставки не оставляет события на повторную доставку.
- Условия: сбой Telegram/proxy длится дольше ограниченных трёх попыток.
- Последствия: событие останется отмеченным, но пользователь его не получит.
- Статус: `FIXED` в текущей рабочей копии.
- Исправление: webhook атомарно фиксирует dedup-маркер и запись SQLite outbox; фоновый worker восстанавливает очередь после перезапуска и повторяет неудачную отправку с backoff. Regression test проверяет отказ Telegram, сохранение после reopen БД и успешный retry.
- Остаточный риск: Telegram `sendMessage` не предоставляет idempotency key. Если Telegram принял сообщение, но подтверждение потерялось до фиксации `delivered_at`, повтор после истечения lease может отправить дубликат. Развёртывание/активность worker и частоту реальных сбоев проверить на runtime по обезличенным timestamp/event ID.
### AUD-03 — P1 · Состояние deal может быть зафиксировано до обновления accounts.json

- Компонент: синхронизация агента / согласованность данных
- Файл: `webhook_server.py:723-754`
- Проблема: `store.save_sync()` коммитит баланс, сделки и снятие команды. После этого выполняется запись `accounts.json` под lock для сервер/holder. Ошибка чтения ключа, шифрования или файловой системы на этом втором этапе вернёт запрос ошибкой, хотя торговые данные уже зафиксированы. Агент повторит пакет, дедуп сделок удержит дубли, но запросы будут повторяться и сведения аккаунта могут отставать от состояния MT5.
- Условия: accounts.json/ключ недоступны или атомарная запись завершается ошибкой после успешной транзакции trades.db.
- Последствия: частичный успех под ответом ошибки; отставание server/holder и повторные запросы; подтверждённая команда уже может быть очищена.
- Исходная рекомендация аудита: согласовать обновление accounts.json с транзакцией или сделать безопасный повторяемый reconciliation этап.
- Runtime deployment check: при плановом обслуживании сверить права accounts-файла и доступность ключа без чтения/печати значений; отказ записи уже проверяется fault-injection тестом на временных данных.

- Статус: `FIXED` для отказа записи `accounts.json`.
- Первопричина: SQLite commit происходил до обновления файла счетов; ошибка файла возвращалась после фиксации sync.
- Исправление: запись `accounts.json` теперь выполняется внутри транзакционной границы `store.save_sync()` до SQLite commit. Ошибка файла/ключа откатывает state, deals и ack; API возвращает HTTP 503, агент может повторить пакет.
- Проверка: fault-injection тест имитирует ошибку записи, проверяет rollback обеих частей и успешный retry. Затронуты `store.py`, `webhook_server.py`, `tests/test_miniapp.py`.
- Остаточный риск: SQLite и `accounts.json` не поддерживают общую crash-safe транзакцию. Аварийное завершение после замены файла, но до SQLite commit, потребует reconciliation.
## 4. Functional bugs

### AUD-04 — P2 · Вывод архива гостевых счетов смешивает разные валюты

- Компонент: бот / расчёт сводного отчёта
- Файл: `bot.py:1436-1474`
- Проблема: `build_all()` складывает суммы архивных месяцев разных счетов в один `by_month[month]['net']`, используя текущую валюту последнего подключённого счёта (`cur`). В Mini App обзор уже группирует личные суммы по валюте, но бот при периоде «Всё время» объединяет, например, USD и EUR без конвертации.
- Условия: один пользователь/кабинет имеет счета в разных валютах и более одного архивного месяца.
- Последствия: месячный график кабинета показывает арифметически сложенные несопоставимые суммы под одной валютой.
- Минимальное исправление: вести отдельную месячную строку для каждой валюты либо не агрегировать разные валюты в одно число.
- Дополнительные данные: для подтверждения реального охвата нужна только проверка валют сохранённых счетов, без чтения паролей.
- Статус: `FIXED` в текущей рабочей копии. Архивные месяцы и общие суммы в `build_all()` агрегируются отдельно по валюте; Mini App приводит личные итоги в USD по текущему официальному курсу НБРБ, опубликованному на MYFIN. Regression test `build_all()` покрывает USD+RUB.

### AUD-05 — P2 · Старый callback отзыва может удалить повторно созданный доступ

- Компонент: Telegram-бот / callback старого сообщения
- Файл: `bot.py:744-764`, `bot.py:2683-2705`
- Проблема: обработчик проверяет лишь, что `guest_by:{uid}` указывает на владельца. После отзыва и повторного приглашения того же uid старое сообщение остаётся доступно; старый callback проходит проверку и отзывает новое отношение.
- Условия: владелец повторно приглашает того же пользователя, пока старое сообщение с кнопкой удаления доступно.
- Последствия: случайный отзыв нового доступа старой кнопкой.
- Минимальное исправление: включить ID/версию приглашения в callback и сверять с текущим отношением перед отзывом.

### AUD-06 — P2 · Переподключение счета через Mini App до проверки реквизитов

- Компонент: Mini App / регистрация счета
- Файл: `miniapp.py:646-686`
- Проблема: новый логин записывается в accounts.json сразу с пользовательским паролем и `pending=True`; корректность сервера, логина и investor-пароля устанавливается только при будущей синхронизации агента. Код блокирует логины, уже известные в accounts или trades DB, но неизвестный ошибочный логин остаётся активной записью и будет постоянно ломать один цикл опроса.
- Условия: опечатка в логине/пароле, неверный server по умолчанию, неподдерживаемый счет.
- Последствия: счёт показывается как ожидающий/устаревший и создаёт ошибки синхронизации; у пользователя нет подтверждения, что credentials приняты.
- Минимальное исправление: ограничить число попыток/статус ожидания и явно переводить запись в подключённое состояние только после валидного sync; сценарий требует уточнения в продуктовой логике.

### AUD-07 — P2 · Share принимает отдельные неверные значения логинов через внутренний helper

- Компонент: учётные записи / API и бот
- Файл: `accounts.py:525-560`
- Проблема: `accounts.share()` перебирает `logins` и делает `int(login)` без проверки типа. `True` превращается в 1, строка-число разбирается как ожидается; Mini App endpoint строго проверяет список и `mt5_login`, но общий helper вызывается также ботом из приглашения. Некорректный/устаревший объект приглашения может выбрать счет 1 или привести к исключению.
- Условия: в сохранённых данных приглашения присутствует булевый/дробный login; обычный пользовательский API это отсекает.
- Последствия: при повреждении/старом формате приглашения может быть расшарен не тот счет или обработчик упадёт.
- Минимальное исправление: валидировать каждый login в общем helper тем же положительным целочисленным контрактом до поиска.

### AUD-08 — P2 · Новое событие-депозит может схлопнуться с совпавшим депозитом в ту же секунду

- Компонент: события кабинета / история движений
- Файл: `partner.py:195-211`
- Проблема: ключ dedup содержит cabinet, timestamp, kind и сумму с двумя знаками; два легитимных одинаковых движения в одной секунде совпадут.
- Условия: два одинаковых депозита одного кабинета/вида/суммы имеют одинаковую секундную метку.
- Последствия: второе движение не попадёт в журнал движений.
- Минимальное исправление: использовать уникальный ID источника, а при его отсутствии хранить оба события и дедуплицировать только по документированному portal event ID.
- Нужны данные: боевой формат ID/времени портала, чтобы выбрать корректный ключ.

## 5. Trading system risks

### AUD-10 — P1 · Trade storage key использует только login, не server

- Статус: `FIXED` (fail-closed защита синхронизации; схема остаётся login-based).

- Компонент: торговая БД / модель идентификатора счета
- Файл: `store.py:15-90`, `store.py:187-216`, `accounts.py:127-156`
- Первопричина: state, deals, months и commands имеют ключи только по login; учётная запись dedup различает физические счета по login+server. `save_state()` раньше лишь писал ошибку в лог при смене server, затем перезаписывал состояние под тем же login. Такое же совпадение ticket у второго счета конфликтовало бы с PK(login,ticket).
- Условия: один номер MT5 встречается на разных серверах (в том числе если сервис сменит брокера или добавит второго).
- Последствия: смешение балансов, сделок, месячной истории и команд между разными торговыми счетами.
- Исправление: `store.save_state()` теперь отклоняет синхронизацию с `ServerMismatchError` до записи; `/agent/sync` возвращает HTTP 409. Транзакция не меняет state/deals/commands, а `accounts.json` не обновляется из отклонённого пакета.
- Проверка: регрессионные тесты проверяют прямой отказ хранилища и HTTP-сценарий с неизменностью баланса, сервера, сделок, команды и `accounts.json`; одинаковый login с тем же server продолжает синхронизироваться.
- Затронутые файлы: `store.py`, `webhook_server.py`, `tests/test_miniapp.py`.
- Остаточный риск: составной ключ не введён. После реального изменения имени сервера синк этого login будет отклоняться до согласованного восстановления; для поддержки нескольких брокеров нужна отдельная миграция всех торговых таблиц и читателей на account_id или `(login, server)`.
- NEEDS_RUNTIME_CHECK: проверить, есть ли в `accounts.json` одинаковые login с несколькими server и расходится ли server аккаунта со `state.server`. `state` имеет PRIMARY KEY(login), поэтому SQL-группировка таблицы `state` не выявит коллизию. На сервере из корня проекта выполнить проверку, которая печатает только агрегаты (без логинов и персональных данных):
  ```bash
  python -c 'import accounts, store; from collections import defaultdict; rows=accounts.load(); by_login=defaultdict(set); [by_login[int(a["login"])].add(a.get("server", "")) for a in rows]; db=store.open_db(); states={int(r["login"]): r["server"] for r in db.execute("SELECT login, server FROM state")}; print("login/server collisions:", sum(len(v)>1 for v in by_login.values())); print("account/state server mismatches:", sum(1 for a in rows if states.get(int(a["login"])) and a.get("server") and states[int(a["login"])] != a["server"])); db.close()'
  ```

### AUD-11 — P1 · При повторном запросе API может подтвердить команду, которую агент не выполнял

- Компонент: торговый агент / очередь команд
- Файл: `agent.py:834-840`, `agent.py:866-877`, `webhook_server.py:723-729`
- Проблема: сетевой retry повторно отправляет неизменный payload при timeout. Если сервер уже зафиксировал первый пакет и удалил команду, ответ потерялся, а во втором пакете снова `command_done=True`; сервер не связывает подтверждение с конкретным command ID и удаляет любую текущую команду для логина. Если в промежутке пользователь поставил новую команду, старый retry её очистит.
- Условия: команда A успешно синхронизирована, ответ POST потерян/timeout, пока команда B записана, повторный POST A до следующего `/agent/accounts`.
- Последствия: команда B теряется без выполнения; race между API-синком и постановкой команды.
- Исправление: команды получают UUID, агент возвращает ID, а сервер удаляет только совпадающую команду внутри транзакции. Дополнительно `command_done` без ID теперь не подтверждает текущую команду. Регрессионные тесты покрывают retry старого ID и отсутствие ID. Агент старой версии, игнорирующий `command_id`, не сможет подтвердить команду до обновления; выкладку сервера следует синхронизировать с обновлением агентов.
- Остаточный runtime check: проверить fault-injection HTTP timeout + постановка новой команды на тестовом стенде; реальные торговые команды не запускать.

### AUD-12 — P2 · Блокирующие MT5 операции останавливают asyncio event loop

- Компонент: бот / клиентская часть MT5
- Файл: `trades.py:201-258`, `bot.py:1702-1845`, `bot.py:2057-2070`
- Проблема: `trades.use()` и MT5 history calls синхронны; Telegram handlers вызывают `build_report()`/`account_totals()` на event loop. Переключение может ждать до 60 секунд, а догрузка истории — до 15 секунд.
- Условия: запрос к счету требует смены MT5 контекста или ожидания загрузки истории.
- Последствия: пока вызов не вернулся, event loop не обрабатывает другие Telegram updates и фоновые задачи.
- Минимальное исправление: сериализовать и вынести MT5 I/O из event loop в один worker/thread, сохраняя один терминальный контекст.
- NEEDS_RUNTIME_CHECK: измерить задержки Telegram polling при первом входе/переключении счёта на Windows машине.

### MONEY-03 — P1 · `max(from_deals, from_agent)` мог удерживать завышенную оценку капитала — `FIXED`

- Компонент: расчёт капитала на сервере
- Файлы: `trades.py:346-375`, `agent.py:897-915`, `store.py:214-228`
- Подтверждено по коду: `_stored_capital()` выбирает больший из двух источников. Текущий агент пытается вычислить `capital_hist` из MT5 с 2000 года; серверная реконструкция из `deals` ограничена `HISTORY_FROM` и свёрнутыми месячными `capital_transfers`.
- Не подтверждено: что в реально работающей установке больший источник устарел после вывода. Источники имеют разную полноту, у `capital_hist` нет отдельной версии/времени успешного расчёта, а текущий `state.synced` обновляется даже если `capital_hist` пришёл `null` и сохранён через `COALESCE`.
- Последствие возможного дефекта: завышенная база процентов/капитала. Простая замена `max()` на минимум/`from_deals` способна недосчитать начальный капитал, потому что сервер хранит историю не с момента открытия счёта.
- Безопасный следующий шаг: на VPS выполнить `python tools/audit.py` по `docs/AUDIT_HOWTO.md`, локально проверить актуальность агента и сверить один известный исторический вывод. Для решения нужны только агрегированный результат и факт актуальности агента; не выгружать БД, `.env`, логины, суммы по строкам или приватные логи.
- Исправлено в текущей рабочей копии: если реконструированная локальная история движений ненулевая, она имеет приоритет; `capital_hist` используется как резерв, когда локальная история отсутствует. Regression test моделирует вывод и устаревший больший `capital_hist`. Runtime-сверка production-данных для этого аудита не выполнялась.

### MONEY-04 — P1 · независимое пополнение на ту же сумму могло отбрасываться — `FIXED`

- Компонент: webhook пополнений
- Файл: `webhook_server.py:184-205`
- Проблема: дедупликация только по типу, кабинету и сумме могла принять два самостоятельных пополнения в пределах окна повтора за одно.
- Исправление: ключ включает валюту; при наличии отличающегося `tx_id`, `transaction_id` или `trans_id` новое событие пропускает дедупликацию как отдельную операцию.
- Проверка: `test_same_amount_with_different_tx_are_both_processed` проверяет два уведомления и две записи ленты для одинаковых сумм с разными ID.
### AUD-13 — P2 · «Профит» и проценты зависят от задержки/полноты истории MT5

- Компонент: агент / расчёт капитала и роста
- Файл: `agent.py:863-915`, `trades.py:682-705`, `trades.py:760-783`
- Проблема: синк получает инкремент после максимального ticket; если источник перестал отдавать старую сделку, алгоритм не имеет watermark по временным диапазонам и не перепроверяет диапазон с перекрытием. Документация отмечает восстановление поздних сделок, но корректность зависит от MT5 history API и доступной глубины на конкретном терминале.
- Условия: брокер позже добавляет/корректирует deal с ticket меньше уже принятого max_ticket либо history выдаёт неполный диапазон после reconnect.
- Последствия: сделка останется пропущенной, а отчёт/капитал будут расходиться с терминалом.
- Минимальное исправление: зафиксировать runtime-поведение MT5 для поздних записей и при необходимости периодически сверять исторический хвост по ticket без повторного влияния дедупа.
- NEEDS_RUNTIME_CHECK: на резервной/тестовой учетной записи сравнить выдачу `history_deals_get` после отключения/повторного входа с сохранённым max ticket; не совершать торговых действий.

## 6. Mini App findings

- Тестовые сценарии Telegram WebView, фактическая safe-area клавиатуры и повторное открытие проверялись документацией/предыдущей историей; текущее состояние реального Telegram клиента требует runtime-проверки.

## 8. Backend and database findings

- AUD-10 и AUD-11 — ключи/ack торговых таблиц и очередь команд.
- `store.open_db()` выполняет расширение схемы при каждом открытии; индексы на `deals.time` и `deals(login,ticket)` есть, но составной физический идентификатор отсутствует.

- SQLite транзакции для синхронизации сделок атомарны, а валидация пакета выполняется до записи; тесты подтверждают rollback на ошибке вставки.
- Схема SQLite не задаёт внешних ключей между trades/state/commands и accounts.json; это намеренно отделённые хранилища, но удаление учетной записи оставляет торговые данные. Это влияет на повторное подключение и retention, не считается дефектом без политики удаления истории.

## 9. Security findings

- Подпись initData и owner checks реализованы в `miniapp.py`; тесты покрывают подделку подписи, просрочку и cross-user доступ.
- SQL формируется параметрами; Mini App статические имена ограничены allowlist; пользовательский текст экранируется на UI и санитизируется для рассылки.
- Пароли шифруются Fernet в `accounts.py`; реальные секреты не выводились и не искались выводом значений.
- AUD-14 — P2 · webhook token помещается в URL и может попасть в access log. `webhook_server.py:71-80`, `webhook_server.py:874`, `docs/findings.md` historical note. Серверный лог явно пишет, что токен находится в URL; nginx access log по умолчанию обычно включает request target. Подтверждён сам URL-контракт, но фактическая маскировка nginx неизвестна. Минимум: проверить установленный nginx `log_format` и, если query логируется, перевести провайдера на заголовок/подпись или маскировать параметры.
- AUD-15 — P2 · общая секретная авторизация агентов даёт каждому держателю `WEBHOOK_TOKEN` доступ к расшифрованным паролям всех включённых счетов через `/agent/accounts`. Это архитектурный blast radius, который сохраняется по контракту. Минимум — machine-scoped credentials/ограничение счетов и процедура ротации. NEEDS_RUNTIME_CHECK для фактической экспозиции ключа/прав машин; значение ключа не запрашивалось.
- AUD-16 — P3 · логирование некоторых исключений/содержимого уведомлений может раскрыть пользовательские сообщения или детали идентификаторов. `bot.py:206`, `webhook_server.py:238`. Проверить retention и доступ к логам на сервере; не найден вывод токенов.

## 10. Architecture and technical debt

- `bot.py` (~3300 строк) смешивает Telegram handlers, фоновые циклы, расчёты и бизнес-операции; `miniapp.py` объединяет HTTP routing, доменную логику и сериализацию; `web/app.js` — один файл с API, навигацией, рендером и dialogs. Это увеличивает риск регрессии, но крупный rewrite не обоснован.
- `trades.py` глобально хранит выбранный MT5 account/config, что снижает тестируемость и усложняет безопасную изоляцию worker-а (AUD-12).
- Авторизация/совместимость аккаунтов распределена между bot, miniapp, accounts и webhook; важные проверки должны оставаться в общих helpers.
- `docs/todo.md` содержит исторические статусы, прошлые runtime deployment и долгий список закрытых задач; датированный статус может быть устаревшим. Не использовать как доказательство текущего production состояния.
- Документация не содержит отдельной актуальной карты архитектуры или roadmap; README покрывает базовый поток и точки запуска.

## 11. Performance

- Отчёт Mini App строит списки движений и сделок после загрузки всех строк по счёту, сортирует их в Python и затем режет страницу. При длинной текущей истории это O(n) чтения и дополнительная память на каждый запрос; архивные месяцы уменьшают, но не устраняют нагрузку для текущего/прошлого месяца.
- В `build_all()` каждый счет отдельно вызывает `trades.monthly(limit=1000)` при «Всё время»; запросы последовательны и происходят в синхронном handler-ом вычислении.
- MT5 отчёты и `trades.use()` синхронны и блокируют asyncio event loop; один запрос может задержать polling и ответы Telegram. См. AUD-12.
- Mini App обновляет данные по таймеру 60 секунд и скрывает обновление в фоне; в коде настроено ограничение частоты API. Архитектурно лишних бесконечных polling циклов не выявлено.

## 12. UX issues

- AUD-06: новый счет остаётся «ожидающим» до первой успешной синхронизации, без проверки credentials в форме.
- AUD-05: старое действие на карточке гостя может отозвать повторно выданный доступ.
- P3 — web UI использует синхронный `toast` для отдельных ошибок, пока фоновые данные остаются старыми; в целом дата последнего обновления и сообщения stale предусмотрены.
- Публичный сайт/регуляторная формулировка лицензии уже помечены в `docs/todo.md` как требующие подтверждения. Репозиторный аудит не может подтвердить юрлицо/статус; не формулируется как технический дефект.

## 13. Tests and reliability

- Запущено в текущей рабочей копии: `python tests/selfcheck.py` — PASS; `python tests/test_miniapp.py` — 128 тестов PASS; `node --check web/app.js` и `python -m compileall -q miniapp.py trades.py tests/test_miniapp.py` — PASS. Реальный парсер сверён с текущей таблицей MYFIN (USD/RUB/BYN).
- В ходе test_miniapp появились `ResourceWarning` об открытых SQLite соединениях в тестовом harness. Тесты завершились успешно; риск production соединений требует отдельной проверки жизненного цикла.
- Playwright UI smoke: исходная проверка зависела от того, что месяц содержит больше данных, чем сегодня, и упала на 1 октября. Сравнение переведено на период «всё время»; повторный запуск был прерван после длительного ожидания и PASS не подтверждён.
- Существенный пробел: тесты AUD-11 покрывают retry старого ID и ack без ID; AUD-04 — раздельную валютную агрегацию `bot.build_all()`; MONEY-03/04 — вывод при устаревшем capital_hist и два одинаковых депозита с разными tx_id; API-тест проверяет перевод USD/RUB/BYN сводки в USD.
- `tests/test_miniapp.py` покрывает HTTP права, sync transaction и многие регрессии, но не интегрирует реальный Telegram transport или MetaTrader5.

## 14. Runtime checks required

1. Общий `WEBHOOK_TOKEN`/машины: сверить владельцев рабочих станций, ротацию ключа и права доступа без чтения его значения; команда на сервере: `systemctl show tagmarkets-webhook -p User,Group` и `stat -c '%a %U:%G %n' /opt/tagmarkets/data/accounts.json /opt/tagmarkets/data/accounts.json.key`.
2. Nginx query logging для webhook URL: `nginx -T 2>/dev/null | rg -n 'log_format|access_log|tagmarkets'`; проверить только конфигурационные строки без URL с действующим токеном.
3. Составные пары login/server: использовать SQL из AUD-10 только на локальной копии/через безопасный audit script, не копируя БД в репозиторий и не печатая личные строки.
4. Поведение MT5 history после длительного offline и ticket correction: на тестовом/резервном аккаунте сравнить результат `history_deals_get` и накопленный max_ticket до/после reconnect; без новых торговых операций.
5. Ошибка `taskkill` и account-file write после SQLite commit: воспроизвести только на изолированной Windows тестовой машине/временной БД; проверить результат команды, HTTP ответ и повтор.
6. Реальное Telegram WebView: проверить вход, клавиатуру/safe area, возврат из фона и обновление stale данных на поддерживаемом клиенте; репозиторный browser smoke не эмулирует Telegram API целиком.

## 15. Proposed improvements

- Выделить маленькие чистые helper-ы для сериализации торгового состояния и обработки команд; не переносить слои целиком.
- Добавить тесты для AUD-12 после утверждения границ исправления.
- Добавить регулярную сверку идентификаторов сделок/состояния и очередь outbox для событий кабинета.
- Зафиксировать совместимые диапазоны Python/dependencies lock-ом после проверки production Python версии; текущие requirements задают нижние границы.
- Добавить документ с актуальными границами компонентов и короткую release/runbook карту только если её будут поддерживать.

## 16. Prioritized remediation plan

### Stage 1 — критические проблемы

1. AUD-10 `FIXED`: конфликт server блокирует sync до записи; миграция составного ключа остаётся необходимой до поддержки нескольких брокеров.
2. AUD-11 `FIXED`: UUID и conditional ack, включая запрет ack без ID; тесты старого retry и пропущенного ID.
3. AUD-01 `FIXED`: ack restart выставляется только после проверки завершения процесса; ошибка сохраняет команду для повтора.
4. AUD-02 `FIXED`: durable webhook outbox с повторной доставкой; остаточная неопределённость — подтверждение Telegram может потеряться после фактической отправки.

### Stage 2 — надёжность

1. Проверить runtime backup/шифровальный ключ, nginx token logging и MT5 recovery по разделу 14.
2. Убрать блокирующие MT5 операции из параллельных Telegram handler-ов или сериализовать общий терминальный контекст (AUD-12).
3. Ввести сверку поздних/скорректированных сделок без изменения финансовых правил (AUD-13).
4. AUD-03 `FIXED` для отказа записи файла; отдельно спроектировать reconciliation для аварийного завершения между двумя хранилищами, если потребуется crash consistency.

### Stage 3 — функциональные дефекты

1. AUD-04 `FIXED`: итоги и архивная сводка по валютам разделены в `build_all()`.
2. Валидировать logins в `accounts.share()` на общей границе (AUD-07).
3. Выбрать устойчивый ID для движений кабинета (AUD-08).

### Stage 4 — UX

1. Показать явные состояния добавления счета: принят, проверяется, подключён, ошибка (AUD-06).
2. Обрабатывать устаревшие callback-и понятным idempotent сообщением (AUD-05).
3. Выполнить Telegram WebView runtime-проверку и исправлять только воспроизводимые проблемы.

### Stage 5 — архитектура/техдолг

1. По мере локальных правок уменьшать ответственность `bot.py`/`miniapp.py` выделением уже повторяющихся доменных операций.
2. Закрыть resource lifecycle (`AppRunner`, DB handles и фоновые задачи) тестом shutdown.
3. Разделить большие отчётные DB чтения и снизить выборку до нужной страницы; подтвердить профилем на копии данных.
4. Обновлять `docs/todo.md` статусы deployment и добавить минимальную architecture map.
